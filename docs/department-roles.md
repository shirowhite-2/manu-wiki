# 网站角色与部门分类访问

网站角色继续决定“能做什么”，部门角色决定“能访问哪些知识库分类”。权限取两者交集，多个部门的分类范围取并集。部门不额外授予编辑、审核、删除或管理员权限；已有的页面禁止访问规则仍有效。

例如：

| 用户配置 | 生效行为 |
| --- | --- |
| 编辑者 + 工程部（工程分类） | 可阅读工程分类，在关联草稿修改，预览并提交审核；不能访问财务分类 |
| 审核者 + 工程部 | 可审核有权访问的工程内容；不能审核其他部门或绕过原有自审限制 |
| 读者 + 工程部 | 只能阅读工程及公共分类；不能因加入部门而编辑 |
| 编辑者 + 工程部 + 财务部 | 可访问两部门分类及其下级，编辑仍须取得草稿编辑权并审核 |
| 未分配部门的普通用户 | 启用限制后只能访问公共分类 |
| Wiki 管理员 | 保留全站管理和访问权限；草稿独占编辑及审核规则仍沿用原流程 |

## 入口和操作

复用 **Wiki 管理 → 用户与权限 → 部门角色**，排列在原生“权限”之后、“用户资料”之前。管理员首页 `XWiki.WebHome` 和左侧管理员导航也保留入口。Mac 端口 8081 的直接地址：

`http://127.0.0.1:8081/bin/admin/XWiki/XWikiPreferences?editor=globaladmin&section=LuxPediaDepartments`

1. 点“创建部门角色”，填写中英文名称，勾选允许访问的知识库分类。
2. 搜索并勾选部门成员，翻页保留选择；列表显示用户已有的网站角色，不改动这些角色。
3. 点“保存部门角色”。部门范围和成员在同一个原生用户组页面中一次保存；多人同时修改时检查版本，后保存者会遇到冲突。
4. 在“分类访问规则”勾选公共分类，再勾选“启用部门分类访问限制”，点“保存访问规则”。这一步单独保存，可在成员和分类配置好后明确启用。
5. 需要撤销部门权限时，编辑部门并移除成员、取消分类或停用部门，再保存。停用后保留原生组及历史，便于恢复。

新安装和升级默认不启用部门限制，以便先配置成员及公共范围，避免已有账号在安装中被批量锁出。启用后，未分配部门的普通用户不会继承全部私有分类。没有选择公共分类意味着没有公共业务分类。

勾选一个分类包含所有下级分类；多部门和公共分类均按这个规则取并集，没有“私有子分类覆盖公共父分类”的隐式规则。若要隔离不同子分类，请分别选择子分类，保持共同父分类不公开。现有原生页面拒绝规则仍可以进一步缩小访问范围。

Knowledge、Drafts 根首页和文档库/分类索引等系统目录沿用原站点权限，方便导航，目录中的业务条目按当前权限过滤。直接位于知识库根目录且不属于已有分类的业务文章不会被部门范围匹配；需由管理员整理到分类中。部门配置不会移动已有文章或附件。

## 草稿、直链和缓存

- Knowledge 文章、分类和其附件继续使用原生 XWiki 鉴权，额外检查部门范围；不能只靠直接 URL 或 REST 绕过分类限制。
- 已关联的 Drafts 草稿按 Knowledge 发布目标判断部门范围。尚未开始工作流、但已保存明确分类的草稿按该分类判断；无法可靠识别分类的历史草稿只允许创建者/原工作区持有人读取，管理员可处理。
- 普通编辑者不能把草稿改投到无权访问的分类。取得编辑权、保存、预览、提交、撤回和审核继续使用既有网站角色、24 小时编辑锁和自审限制。
- 页面浏览器、收藏、导航、审核队列和使用原生鉴权的搜索结果会过滤无权访问的条目。启用部门限制时，普通用户的标准 Solr 搜索会关闭全局分面、摘要高亮、调试数据和精确总数展示，使用上一页/下一页浏览，避免原生全局统计描述不可见内容。原生结果行鉴权仍保留；管理员和未启用限制时沿用原搜索。自定义搜索应用需接入同样保护。仍已下载、导出或留在浏览器中的内容不会因撤权被追回。
- 部门范围不缓存为永久授权：每次读取原生授权结果都核对当前规则和草稿目标，也会复查已存储的部门成员。因此移除成员、停用部门或取消分类后，旧的授权缓存不能继续授予该范围。原生用户组新增成员仍由 XWiki 的组缓存失效机制生效。

## 实现与后续账号系统

部门保存为 `XWiki.LuxDepartment_<固定ID>` 原生用户组，成员使用 `XWiki.XWikiGroups`，范围和名称由受保护的 `LuxPedia.Code.DepartmentClass` 对象记录。可以从原生用户组管理器查看。原生组嵌套团队可继续参与匹配，服务端检查循环及深度；本界面主要勾选用户，并保留原有有效原生组成员。

`LuxPedia.Code.DepartmentSettings` 仅管理员可读写，记录总开关和公共分类。管理接口要求真实 Wiki ADMIN，写入另需 POST、CSRF 和文档版本；部门名称不会成为可任意指定的网站角色组名。

使用 XWiki 官方可配置的 `AuthorizationSettler` 扩展点，先保留默认原生判定，再收窄业务页的查看、编辑、评论、删除权限。配置为：

```properties
security.authorization.settler=luxpedia-departments
```

此 JAR 不开放 Docker 控制权限，也不引入第二套账号或登录系统。以后接若依/LDAP/AD 时，可分别映射网站角色组和部门组；身份同步本身未在本次实现。非 Docker 部署需运行 `sh extensions/workflow-policy/configure-departments.sh /实际路径/WEB-INF/xwiki.properties` 并重启；若已有其他自定义授权 Settler，必须先合并两个集成，脚本会保留现有配置并退出。

## 升级（策略 15，Mac 端口 8081）

保留原 `.env`、`.secrets`、Compose 项目名、数据库与 XWiki 数据卷，按现有流程备份后，在项目目录执行：

```bash
git switch feat/article-translation &&
git -c http.version=HTTP/1.1 pull --ff-only origin feat/article-translation &&
docker run --rm -v "${PWD}:/workspace" -v manu-wiki-maven-cache:/root/.m2 \
  -w /workspace maven:3.9-eclipse-temurin-17 \
  mvn -f extensions/workflow-policy/pom.xml clean package &&
docker compose -f compose.yaml -f compose.workflow-policy.yaml \
  up -d --build --force-recreate --wait xwiki &&
NO_PROXY=127.0.0.1,localhost no_proxy=127.0.0.1,localhost \
  python3 scripts/apply_workflow.py --base-url http://127.0.0.1:8081 --apply
```

策略 12 及以前也要重建 JAR 和镜像。Dockerfile 会配置原生授权扩展，并在官方启动脚本恢复旧配置之后、启动 Tomcat 之前再次应用此配置，避免数据卷里的旧配置覆盖新设置；安装器同时检查请求写入守卫和部门授权扩展，缺失时停止。升级保留既有草稿、附件、编辑租约和网站角色。完成后强制刷新浏览器，再配置并启用部门限制。仍按本仓库单 XWiki 节点部署。

## 权限页的两个匿名用户开关

原生页面有两个独立配置：`authenticate_view`（强制登录后查看）和 `authenticate_edit`（强制登录后编辑）。已补齐明确的中英文名称，并按原生输入框身份绑定文案，保留输入框、勾选状态和原有自动保存事件。不会因为文字重复而删掉其中一个安全选项。

## 验收

用管理员先建立工程、财务及公共三个分类；给编辑者 A 分配工程部，审核者 B 分配工程部，编辑者 C 分配财务部，读者 D 分配工程部；另保留一个未分配部门的普通用户。启用后验证：

1. A/B/D 可读工程及公共分类，C 只能读财务及公共分类；未分配部门者只能读公共分类。D 不能编辑，A 不能审核自己的文章。
2. A 对工程文章打开关联草稿，B 可读和审核，C 打开草稿、正文直链、REST 或附件直链均被拒绝。A 不能把草稿提交到财务分类。
3. 管理员给 A 加入财务部后，可访问两部门范围；移除工程成员资格或工程分类授权后，刷新旧链接立即不能访问工程内容，即使仍持有旧草稿编辑租约。
4. 搜索、页面浏览器、收藏、审核队列及分类树不显示无权访问的文章；用实际实例检查原生搜索、附件下载、版本历史和导出行为。
5. 两个管理员同时改同一部门，后保存者遇到版本冲突；普通账号直接请求管理接口不返回部门成员或配置，伪造 POST 不能修改组或范围。
6. 权限页“强制登录后查看/编辑”各只有对应功能文案，切换语言保留勾选状态，点编辑开关不会改变查看开关。

自动检查包括原生授权扩展接口、缓存结果撤权、部门并集、公共/未分配/管理员/访客、草稿目标、原生组嵌套与循环、单文档保存、版本冲突、POST/CSRF、原生管理分区注册、配置脚本以及浏览器成员选择和双语输入。未连接用户 Mac 执行真实账号切换或修改真实权限；部署后应按上述矩阵验收，再向所有用户启用。
